# Naming inventory: working rules

This vault records what a design system's names are **today**, and where they disagree.
It works with or without Claude.
Every note follows a template in `templates/`, and a note filled in by hand is as valid as one Claude filled in.

## Folders

| Folder | Holds | Template |
|---|---|---|
| `exports/` | Raw exports: Specs YAML or JSON, variable CSVs, DTCG token JSON | none, kept exactly as exported |
| `conventions/` | The system's own documented naming conventions, if it has any | `templates/naming-convention.md`, or `templates/property-conventions.csv` as a spreadsheet |
| `components/` | One note per component | `templates/component.md` |
| `tokens/` | One note per variable collection | `templates/token-collection.md` |
| `findings/` | One note per naming disagreement | `templates/naming-finding.md` |
| `decisions/` | One record per naming decision | `templates/decision.md` |

Name notes after the thing as it is named in Figma: `components/toggle-button.md`.

## Rules

**1. Record, don't fix.**
Inventory notes describe what exists.
A disagreement becomes a finding; a new name becomes a decision, chosen by people.
Never rename anything in an inventory note to make it tidier.

Never rename anything at the source either: not in Figma, not in token files, not in code, and not even to remove emojis.
A name is a contract that designs, code and pipelines depend on.
Renaming it is a breaking change, and it goes through a decision and a release, not an inventory.
If asked to "clean up" names, record the findings and stop.

**2. A naming rule is bound to its domain.**
Before calling two names inconsistent, check that they are on the same domain.
A Figma variable (`color/bg/accent`), a token path (`color.bg.accent`) and a CSS variable (`--color-bg-accent`) differ because each domain requires it.
That is not an inconsistency, and flagging it wastes everyone's time.

**3. A difference is not always an inconsistency.**
Ask whether the things themselves differ.
A toggle button has a selected state and a button does not, so only one of them has `isSelected`.
That is correct.

**4. Missing from the export is not missing from the file.**
Every export leaves something out.
The free tier of the Specs plugin writes colours as raw hex even when variables are applied in Figma.
Never conclude that a component is not tokenised from an export alone.
Write "the export doesn't show variables", not "no variables".

**5. Leave judgement cells as `?`.**
Don't guess framework part names, code prop names, or who decided something.
A wrong answer in a table reads as settled; a `?` reads as a question, which is what it is.
A made-up attribution is worse than an empty field.

A framework part name or code prop filled in from an AI answer, including your own, needs a link to the framework's documentation in the cell or its note.
No link, no answer: leave `?`.

**6. Use names exactly as Figma has them.**
Take the component's `title` from a Specs export, not the key above it.
The key (`toggleButton`) is generated by the plugin; the title (`toggle-button`) is what the designer typed.

**7. Mark inferences.**
If a cell is worked out rather than read, say so: `focus-outline? (inferred)`.

**8. Count with a script, not by eye.**
Token and variant counts go in reports and get quoted.
Run a script to count them.

**9. Ask before overwriting a person's note.**
If a note already exists, ask first.
If it is committed to git, say that the difference will show in GitHub Desktop.

**10. Keep frontmatter strict-YAML-safe.**
Quote any value that contains `: `, starts with a special character, or is a template placeholder like `"{{date}}"`.

**11. Read the conventions before judging anything.**
If `conventions/` holds the system's documented conventions, read them before classifying any difference.
A pattern that looks inconsistent (`svg-icon-start` beside a boolean `icon-start`, camelCase `isSelected` beside kebab-case `interaction-state`) may be a deliberate, documented rule.
Against a documented convention, the finding is "this component doesn't follow it", which also says which side to fix.
If there are no documented conventions, say so: that is a finding too.

**12. A token's tier is decided by its value, not its name.**
A token that holds a raw value (`#5B81FE`, `16px`) is a primitive, whatever it's called.
A token that references another token is not, even if its name reads like a primitive (`font-family-lato`).

## Skills

| Skill | Use it for |
|---|---|
| `inventory-component` | A Specs export, or another plugin's component export, turned into a component note |
| `inventory-tokens` | A variables CSV or DTCG token file, turned into a naming grammar |
| `naming-findings` | Comparing the notes and writing up where names disagree |

## Question IDs

Templates cite question IDs such as `P-07` or `T-04`.
They refer to the naming decision inventory: the list of naming decisions a design system has to make, and what already settles each one.
